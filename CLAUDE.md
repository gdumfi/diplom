## 1. Что это и в чём суть

Инструмент автоматического анализа безопасности смарт-контрактов.

**Ключевая идея, отличающая от конкурентов:** транслируем Solidity → **LLVM IR** (а не в
EVM-байткод, как Slither/Mythril/Manticore), и весь анализ строим поверх LLVM IR. Это даёт
доступ к зрелой compiler-grade инфраструктуре (готовые проходы анализа, SSA, символьный движок KLEE).

**Конечная ценность продукта:** не «нашли подозрительный паттерн» (это умеет бесплатный Slither),
а **автогенерация работающего PoC-эксплойта**. За это платят.

## 2. АРХИТЕКТУРНЫЕ РЕШЕНИЯ (менять только с явным обоснованием И согласованием)

### AD-1. Язык анализатора — C++20 на нативном LLVM API
Анализатор пишется на C++20 напрямую через LLVM C++ API (не Python/llvmlite, не парсинг текста `.ll`).
*Обоснование:* нативный `PassManager`, `DominatorTree`, `CallGraph`, CFG-итераторы; один язык с фронтендом.

### AD-2. Единая версия LLVM — 18.1.x
Жёстко зафиксирована для фронтенда, анализатора и KLEE. **Проверять версию на каждом компоненте.**
*Обоснование:* формат IR меняется между мажорами; рассинхрон версий = самый частый источник потерь времени.
*Факт:* фронтенд уже собран на LLVM 18.1 (`/usr/lib/llvm-18`).

### AD-3. EVM-семантика сохраняется в IR явно — ✅ РЕШЕНО: address spaces
При трансляции НЕ терять блокчейн-семантику (storage / external call / msg.sender / revert), а кодировать
её в структуру IR. Это фундамент — блокер для всего анализа.
**Решение (2026-07-10):** storage = `addrspace(1)` pointer-модель (вариант B). Текущий codegen на
интринсиках `@evm.sstore/@evm.sload` **мигрируем** на `store/load ... ptr addrspace(1)`.
*Обоснование:* ближе к compiler-grade, сильнее в дипломе; детект reentrancy = «store в addrspace(1)
после `@scsa.external_call`». `@evm.msg_sender/msg_value/revert` остаются интринсиками (это контекст/поток
управления, не storage).

### AD-4. Два слоя анализа: CFG-детектор первым, KLEE вторым
Сначала CFG-обход (без символьного исполнения) → работающий продукт за недели, near-zero false-positive
на явных случаях. KLEE — потом и **только на путях, которые CFG уже пометил подозрительными**
(приём против экспоненциального взрыва путей). Начинать с KLEE = застрять без демо.

### AD-5. Один бинарь `sca` — это и есть продукт
Вся логика анализа в одном C++ executable. Веб/бэкенд только вызывают его и парсят JSON.
**Никогда не переносить логику анализа в веб-бэкенд.**

### AD-6. Приоритет уязвимостей по «деньги × достижимость», не по популярности
Reentrancy — демонстрация метода (делаем первой технически). Access control — главная коммерческая
ставка (второй виток). См. раздел 7. *Обоснование:* защита от ошибки выжившего.

### AD-7. Ров продукта — автогенерация PoC, не детекция
Детекцию reentrancy/access-control Slither делает бесплатно. Устойчивая ценность = экономия часов
аудитора/хантера на написании рабочего эксплойта.

## 4. EVM-семантика в LLVM IR (ТЕХНИЧЕСКОЕ ЯДРО)

### 4.0. Схема storage — ✅ РЕШЕНО: address spaces (вариант B)
Storage = `store/load i256 %v, ptr addrspace(1)` (см. 4.1). Текущий codegen на интринсиках
`@evm.sstore/@evm.sload` мигрируем на pointer-модель. Детектор reentrancy ищет «store в `addrspace(1)`
после `@scsa.external_call`». `@evm.msg_sender/msg_value/revert` остаются интринсиками.

### 4.1. Address spaces
| EVM | addrspace | Семантика |
|-----|-----------|-----------|
| storage | `addrspace(1)` | постоянное состояние, переживает транзакцию |
| memory | `addrspace(2)` | временное, одна транзакция |
| calldata | `addrspace(3)` | входные данные, read-only |

### 4.2. Внешние вызовы через кастомный интринсик — БЛОКЕР, ещё не существует
`CALL`/`DELEGATECALL`/`STATICCALL` передают управление недоверенному коду.
```llvm
call void @scsa.external_call(...)   ; управление уходит наружу, может вернуться (callback)
```
Интринсик несёт метаданные: доверенный/недоверенный target; какие storage-слоты доступны для
реентрантной модификации; тип вызова (call/delegatecall/staticcall — delegatecall особо опасен).

### 4.3. Контекст транзакции
`msg.sender`, `msg.value`, `tx.origin`, `block.timestamp` — глобальны для EVM. Уже частично есть
(`@evm.msg_sender`, `@evm.msg_value`). Для KLEE-слоя моделировать как символьные глобальные значения.

### 4.4. Revert-семантика
`require`/`revert` откатывает ВСЁ состояние транзакции. Уже есть `@evm.revert` (noreturn). Для KLEE
моделировать явно, иначе решит, что после revert состояние сохраняется → ложные пути.

## 5. Логика детекторов

### 5.1. ReentrancyPass (ядро MVP)
```
Для каждой функции:
  1. Построить CFG (llvm::CFG из коробки)
  2. Найти все вызовы @scsa.external_call
  3. Для каждого — обход графа ВПЕРЁД от точки вызова (reachability по DominatorTree)
  4. Если на достижимом пути ПОСЛЕ вызова есть запись в storage (sstore / addrspace(1) store)
     → REENTRANCY (нарушение checks-effects-interactions)
  5. Проверить nonReentrant-guard (флаг в storage выставлен/проверен до вызова) → снизить/снять severity
```
**Из LLVM (не писать своё):** `PassManager`, `DominatorTree`, `predecessors()/successors()` на
`BasicBlock`, `CallGraph` (межфункциональный, 2-й виток). Прогнать `mem2reg` ПЕРЕД анализом → чистая SSA.

### 5.2. AccessControlPass (денежная ставка, 2-й виток)
Для критических функций (меняют owner / выводят средства / totalSupply / параметры): есть ли проверка
прав (`msg.sender == owner`, `onlyOwner`)? Символьно — существует ли caller, дошедший до опасной
операции без проверки? **Честная граница:** простые случаи (нет модификатора) — легко; неверная логика
прав / испорченная инициализация — требуют понимания намерения, автомат ограничен.

## 6. Моделирование внешнего мира (для KLEE-слоя, 2-й виток)

Ключевой вопрос — **кто контролирует адрес** (доверенная граница). Стратегии по приоритету:
1. **Havoc** (дефолт для недоверенных): худший случай — возврат символьный, возможен реентрантный
   callback в любую публичную функцию. Консервативно, без пропусков, но с false-positive.
2. **Ветвление на reentrancy-callback глубиной 1** (ядро): в точке `@scsa.external_call` форкаем на
   мир A (вернулись нормально) и мир B (атакующий из callback снова зовёт публичную функцию → перезапуск
   символьного исполнения → если storage не обновлён, деньги выводятся повторно → баг с путём). Глубина 1–2.
3. **Summaries** (позже): краткие модели известных контрактов (ERC20 transfer). Библиотека = отдельный актив.
4. **Символьный target-адрес** (2-й виток): ловит arbitrary external call / unchecked delegatecall.
