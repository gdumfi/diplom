# ROBUSTNESS-PLAN — снять долю SKIP фронтенда на реальных 0.8 (data-driven)

> Цель — прямой рычаг к реальному recall. Сейчас в живой батч-воронке (`hunt_batch.sh`)
> ~90% реальных контрактов SKIP-аются (не доходят до IR), поэтому вся мощь детекторов и
> forge-инвариантов работает только на демо. Пока это не снято, «найти реальный баг» упирается
> сюда. План строится ПО ДАННЫМ: сначала измерить причины, потом чинить по частоте.

## 0. Ключевая находка (определяет приоритеты)

Разбор кода (2026-07-12): **`AstJsonLowering` уже деградирует мягко** — неизвестные выражения/типы
(bytes/string/struct/enum/asm/builtin) лоуэрятся в opaque `i256` или маркер `@scsa.opaque_store`,
а НЕ прерывают анализ. Жёсткие `diag.error` — только на верхнем уровне: пустой JSON, нет sources/AST,
или итоговый IR не прошёл верификацию (`AstJsonLowering.cpp:1217/1229/1235/1254`).

Вывод: **SKIP концентрируется на слое ВЫЗОВА solc, не в покрытии узлов лоуэринга.** Живой замер это
подтвердил: 0.4-контракты падают как «версия вне охвата» (мы звали solc 0.8.19 вместо их версии),
один 0.8 — «solc: TypeError» (несовпадение версии/настроек). Значит самые дешёвые и крупные фиксы —
инфраструктурные (версия/образ/standard-json settings), а не «добавить N узлов в лоуэринг».

## 0.1. Результат замера 0c (2026-07-13) — КОРРЕКТИРУЕТ ПРИОРИТЕТЫ

Directional-выборка (`hunt_batch.sh`, RESULTS.md «Robustness baseline»): крупные реальные **0.8**
(Seaport 1.1/1.5, Permit2, 1inch V5) лоуэрятся **успешно, 0 отказов A1/A3/B1** (4/4); 0.4-ханипоты →
`[C]`. Вывод: **доминирует бакет C (pre-0.8) — честная граница, не баг**; 0.8-путь уже рабочий даже
на assembly-heavy контрактах. Ранняя оценка «~90% SKIP» была из 0.4-heavy выборки.
**Ревизия:** Фаза 1 (робастность лоуэринга) — НИЖЕ приоритет; больший рычаг к recall = фильтровать
цели на 0.8 + покрытие детекторов/инвариантов. Полное подтверждение требует случайного 0.8-корпуса
(нужен RPC без 128КБ-капа). Инструментовка (0a) остаётся — ею меряем при появлении такого корпуса.

## 1. Цель и метрика успеха

- **Метрика:** доля реальных **0.8.x**-контрактов, доведённых до валидного IR (`lower-success rate`),
  на фиксированном корпусе из N (цель N≥150). Замер до/после каждого фикса.
- **Стартовая гипотеза:** baseline низкий из-за версии/настроек; после Фазы 1a-1b — резкий скачок.
- **Границы честности:** цель — **0.8.x** (современный, денежный сегмент). `<0.8` (0.4–0.7) —
  ЯВНО вне охвата (AstJsonLowering заточен под 0.8-AST), помечаем reason-ом, не «чиним».
- **Не регрессировать:** 191/191 юнит-тест + `corpus08` P/R=1.0 + `smartbugs` recall — зелёные после
  каждого шага (инвариант «downstream читает только IR» не трогаем).

## 2. Модель причин SKIP (что бакетим)

Слой A — **вызов solc** (`SolcRunner`/`Driver`/`EtherscanFetch`):
- A1. нет docker-образа `ethereum/solc:<ver>` (не запулен) → «нет вывода solc».
- A2. версия не та: звали дефолт 0.8.19 вместо версии контракта → solc отвергает исходник
  («requires different compiler version», «Data location must be specified», …).
- A3. неполный standard-json: не переданы optimizer/evmVersion/remappings/libraries/viaIR из
  метаданных Etherscan → solc не собирает как при деплое.
- A4. multi-file/import: не все sources или неверные remappings.

Слой B — **лоуэринг** (`AstJsonLowering`):
- B1. IR не проходит verifier (баг лоуэринга конкретного узла) → abort (:1217).
- B2. по-настоящему неучтённый узел, ломающий семантику (редко — обычно уходит в opaque).

Слой C — **не баг:** `<0.8` вне охвата (честный SKIP), либо реально чистый контракт.

## 3. Фаза 0 — Инструментовка + корпус (СНАЧАЛА измерить)

**0a. Точная таксономия отказа в бинаре.** Сейчас SKIP-reason грубый. Добавить структурный код
причины (A1/A2/A3/A4/B1/B2/C) в вывод `Driver` (stderr-тег или поле в JSON), чтобы `hunt_batch.sh`
бакетил не по эвристике grep, а по коду. Мини-изменение в `Driver.cpp`/`SolcRunner.cpp`.

**0b. Feeder реального 0.8-корпуса** (`benchmarks/hunt_feeder.sh`):
- через Alchemy RPC: пройти последние K блоков → tx с `to==null` (создание контракта) →
  `eth_getTransactionReceipt.contractAddress`;
- по каждому адресу Etherscan `getsourcecode` → взять только `CompilerVersion` c `v0.8.` и
  `SourceCode != ""` (верифицирован); отсеять прокси/дубли;
- накопить N≥150 адресов в файл (вход для `hunt_batch.sh --addrs`).
- Быстрый старт (пока feeder пишется): публичный датасет верифицированных 0.8-контрактов для замера.

**0c. Baseline-замер.** `hunt_batch.sh --addrs corpus0.8.txt` → распределение по бакетам A1–C.
Зафиксировать в `benchmarks/RESULTS.md` (раздел «robustness»). Это карта — что чинить первым.

## 4. Фаза 1 — Чинить по частоте (ожидаемый порядок; финальный — по данным 0c)

**1a. Точная версия solc на контракт + доступность образа (ожидаемо крупнейший бакет A2/A1).**
- Убедиться, что `EtherscanFetch` реально извлекает `CompilerVersion` и Driver его использует
  (живой замер намекает, что падает в дефолт 0.8.19 — проверить и починить парсинг тега).
- Маппинг `v0.8.X+commit…` → docker-тег `0.8.X`; `docker pull` при отсутствии (кеш образов).
  Для батча — префетч набора 0.8.0–0.8.28 один раз.

**1b. Достоверные standard-json настройки (бакет A3).**
- Пробросить в `--standard-json` `settings` из метаданных Etherscan: `optimizer{enabled,runs}`,
  `evmVersion`, `remappings`, `libraries`, при наличии `viaIR`. Тогда solc принимает исходник как
  при деплое (снимает часть «TypeError»/строгостей).

**1c. Multi-file/remappings (бакет A4).** Проверить, что все sources и remappings из Etherscan
(`fetchVerifiedSources` уже их возвращает) корректно доходят до `runSolcMulti`; добить крайние случаи
(вложенные пути, `@oz/…`).

**1d. Явный scope-guard `<0.8` (бакет C).** Если `CompilerVersion < 0.8` — сразу помечать
`out-of-scope (pre-0.8)` и не тратить solc-прогон. Честно и быстро; не «фикс», а классификация.

**1e. Лоуэринг: verify-fail → graceful (бакет B1).** Когда итоговый IR не верифицируется, вместо
общего abort — локализовать сбойный узел и заменить его на opaque-фолбэк (принцип: **деградация, а не
падение**; downstream всё равно проанализирует остальное). Логировать, что стало opaque (без тихой
потери — правило «no silent truncation»).

**1f. Только теперь — топ реально неучтённых 0.8-конструкций (бакет B2, по данным 0c).**
Добавлять лоуэринг ИЛИ opaque-фолбэк узла по убыванию частоты. Кандидаты-подозреваемые (проверить
замером, не гадать): custom errors, `try/catch`, enum-в-storage-слоте, вложенные `mapping(=>mapping)`,
библиотеки с состоянием, function-types, `unchecked`-блоки, `abi.decode` в таргет вызова.

## 5. Фаза 2 — Пере-замер и цикл

После каждого фикса 1a→1f: повторить 0c на том же корпусе, записать новый lower-success rate в
`RESULTS.md`. Остановка — когда кривая выходит на плато или достигнут целевой % (напр. ≥60% 0.8.x).
Каждый виток — коммит + строка в HISTORY.

## 6. Гардрейлы

- **Downstream читает только IR** (несущая стена, CLAUDE.md AD-3/AD-4) — не нарушать.
- **Деградация > падения:** неизвестное → opaque + лог, не abort.
- **Зелёные тесты:** 191/191 + `corpus08` P/R + `smartbugs` recall после каждого шага.
- **No silent truncation:** что ушло в opaque / было пропущено — логируется (иначе «покрыли всё» врёт).
- **Честный scope:** `<0.8` — не притворяемся, что чиним; помечаем и идём дальше.
- **CODE-MAP/RESULTS в синхроне** в том же коммите.

## 7. Первый конкретный шаг

**Фаза 0a+0b+0c за один заход:** (1) добавить структурный reason-код в `Driver`/`SolcRunner`;
(2) написать `hunt_feeder.sh` (RPC block-walk → 0.8-адреса); (3) собрать N≥150 и прогнать
`hunt_batch.sh`, получить baseline-распределение бакетов. Это даёт карту, по которой Фаза 1 чинит
по реальной частоте, а не по догадкам. Ожидание из живого зонда: доминируют A2/A1 (версия/образ) —
тогда 1a даёт наибольший скачок при наименьшем коде.
