## KLEE — символьное подтверждение эксплойта (2026-07-11, ядро новизны)

Полный конвейер защищаемого метода: **Solidity → LLVM IR (с EVM-семантикой) → KLEE-понижение
(`--emit-klee`) → символьное исполнение → подтверждённый эксплойт с конкретной моделью**.

Бэкенд: официальный docker-образ `klee/klee` (**KLEE 3.2 на LLVM 16.0.6**). Наш IR эмитится как
текстовый LLVM 18, но текстовый `.ll` переносим — `llvm-as` LLVM 16 внутри образа принимает его без
изменений. Прогон: `benchmarks/run_klee.sh <файл.sol>` (авто-бэкенд docker/локальный).

**Обобщение на корпус (`run_klee_corpus.sh`, независимый клон SmartBugs):**

| | Значение |
|---|---|
| CFG-находок HIGH reentrancy | 28 |
| понижение в KLEE-модуль | 28/28 |
| **KLEE ПОДТВЕРДИЛ (достижим путь кражи)** | **28/28 = 1.00** |
| KLEE чисто (путь не достижим) | 0 |
| контроль precision: CEI-safe + guarded | **оба ЧИСТО (0 ложных подтверждений)** |

KLEE символьно подтверждает **все 28** реальных reentrancy из клона (single-attacker, глубина 1) и
**отвергает** безопасные паттерны (CEI-порядок, nonReentrant-guard) → символьный слой соунден
(0 ложных подтверждений) и на этом корпусе полон. Пороговый оракул: `total_sent > storage[effectSlot]`,
где effectSlot — слот записи-эффекта после вызова (из находки); сравнение именно с ним, а не с суммой
всех слотов, ловит многослотовые контракты (`etherstore`: вывод против `balances`, не против
`withdrawalLimit`). Балансы ограничены `< 2^128` (`klee_assume`) — оракул без переполнения i256.
Блок-контекст (`block.number/timestamp`) символьный (§4.3) → гарды вида `block.number > lastBlock`
не схлопываются в ложь (`0x941d…`).

| Пример | CFG | KLEE | Модель |
|---|---|---|---|
| `reentrancy.sol` (Vault, эффект после вызова) | HIGH | **ERROR: funds sent exceed balance** | balance/reenter=1 |
| `etherstore` (лимит вывода, многослотовый) | HIGH | **ERROR** (effect-slot оракул) | — |
| `0x941d…` (гард block.number) | HIGH | **ERROR** (символьный block.number) | — |
| CEI-safe / nonReentrant-guard (контроль) | чисто | **нет ошибки** | — |

### Символьное подтверждение access-control (денежная ставка #1, $953M)

Метод обобщён на второй класс уязвимостей — **не заточен под reentrancy** (усиливает компонент #2
диплома «переиспользование KLEE»). `--emit-klee --klee-mode access-control`: понижение инструментирует
записи в привилегированный слот флагом `priv_written`; харнесс снимает owner на входе и символизирует
msg.sender; оракул — `priv_written ∧ (msg.sender ≠ owner)`: привилегированная запись достижима при
не-владельце → отсутствие контроля доступа. Слоты (privSlot, ownerSlot) прокидываются из
`AccessControlDetector` (или вручную `--klee-slot/--klee-owner-slot`).

| Контракт | CFG | KLEE | |
|---|---|---|---|
| `ac_vuln` (`setOwner` без проверки) | HIGH | **CONFIRMED** (ERROR: privileged state changed by non-owner) | атакующий перехватывает owner |
| `ac_safe` (`setOwner` с `require(msg.sender==owner)`) | clean | **CLEAN** | путь к записи требует msg.sender==owner → оракул недостижим |

Соундность: `require(msg.sender==owner)` становится ветвлением, констрейнящим путь к привилегированной
записи на `msg.sender==owner` → `not.owner` ложно → CLEAN. Уязвимый (нет проверки) → любой msg.sender
достигает записи → `msg.sender≠owner` выполнимо → CONFIRMED. Фикстуры: `benchmarks/klee_access_control/`.

**PoC для access-control** (`--poc`, `PocGenerator::generateAccessControl`): Foundry-тест, где
атакующий (не владелец, `vm.prank`) вызывает привилегированную функцию (`target.setOwner(attacker)` —
address-аргумент = attacker, забирает владение). Защищённая функция здесь ревертнула бы; прохождение
теста без revert = контроль доступа отсутствует. С KLEE-witness помечается «СИМВОЛЬНО ПОДТВЕРЖДЁН».
Пайплайн для обоих классов: CFG-находка → KLEE-подтверждение → PoC.

### Негативный корпус: KLEE-слой НЕ тавтология CFG (`klee_negative.sh`)

Прямой ответ на вопрос защиты «не подтверждает ли KLEE ровно то, что нашёл CFG?». Прогоняем
безопасные и CFG-переflagged контракты через KLEE **принудительно** (`--klee-entry`, минуя CFG-gate):

| Контракт | CFG | KLEE | |
|---|---|---|---|
| `safe_cei` (обнуление до вызова) | clean | **CLEAN** | соундность |
| `bool_guard` (nonReentrant, распознан) | LOW-guard | **CLEAN** | соундность |
| `counter_guard` (guard на счётчике `status==0`) | **HIGH** | **CLEAN** | **CFG→KLEE precision gain** |

`counter_guard` — reentrancy-паттерн с nonReentrant-guard **на счётчике** (не `bool !flag`), который
CFG-эвристика распознавания guard не ловит → ложный HIGH. **KLEE отвергает** его: реентрантный заход
ревертит на `require(status==0)`. **0 ложных подтверждений KLEE** на всём негативном корпусе → символьный
слой соунден (отвергает безопасное) И уточняет CFG (снимает ложный HIGH) — это refine, а не эхо.

*Оговорка соундности (проверено эмпирически, не дельта-инвариантом): оракул `total_sent > snapshot`
корректен, т.к. при CEI списание-до-вызова ограничивает реентрантную сумму (require видит уменьшенный
баланс → total_sent ≤ snapshot), а при эффекте-после-вызова — нет (до 2·B > B). Баланс-дельта-инвариант
`snapshot−final` здесь НЕВЕРЕН: в old-Solidity баланс underflow'ит и суммарное списание == total_sent,
что маскирует реальную кражу (ломает 28/28 → 6/28). Граница модели: single-attacker, глубина 1, ключ
mapping схлопнут в один слот → multi-user vault может дать ложное подтверждение (документированный non-goal).*

**Оракул KLEE precise:** true positive на уязвимом (символьно достижим путь `total_sent > баланс`
через fork реентрантного callback глубины 1, §6.2), **0 ложных** на CEI-safe.

**PoC без TODO (ров, AD-7).** `run_klee.sh` извлекает witness-модель из ktest (balance, msg.value) и
генерирует **символьно подтверждённый** Foundry-PoC: шапка «reentrancy — СИМВОЛЬНО ПОДТВЕРЖДЁН KLEE»
+ witness (`balance ≥ 1 wei`, msg.value, глубина) + оракул. Это не «подозрительный паттерн» (Slither),
а доказанный достижимый путь кражи — устойчивая ценность продукта. Спекулятивные `TODO(hunter)` сняты
(остаётся честный TODO про форк боевой жертвы — ортогонален подтверждению уязвимости).

`git clone smartbugs-curated`, датасет reentrancy: **31 контракт**. После итераций расширения
фронтенда под боевой Solidity 0.4.x:

| | Значение |
|---|---|
| скомпилировалось | **29 / 31** (было 0 → 4 → 8 → **29**) |
| из них найдено (TP) | **28** |
| пропущено (FN) | **1** (modifier_reentrancy — см. ниже) |
| **recall на скомпилированных** | **0.966 (28/29)** |

Компилируются и корректно ловятся (HIGH) все семейства reentrancy из датасета: SimpleDAO/EtherStore,
trailofbits Reentrance, cross-function, bonus, а также **honeypot-семейство PERSONAL_BANK/PrivateBank**
(20 файлов `0x…`) с *немодифицированным* исходником из клона. Honeypot'ы включают storage-ссылку
старого Solidity (`var acc = balances[msg.sender]; … acc.balance -= _am` после внешнего вызова) —
это моделируется как запись в storage, поэтому reentrancy ловится.

**Единственный FN — `modifier_reentrancy.sol`:** реентрантность идёт через *высокоуровневый*
внешний вызов в модификаторе (`Bank(msg.sender).supportsToken()`) до тела функции. Такие типизированные
кросс-контрактные вызовы мы намеренно моделируем как opaque (не `@scsa.external_call`), чтобы не
жертвовать precision (иначе `token.transfer()` в безопасном коде рискует дать FP). Задокументированная
граница: снимется вместе с моделью «типизированный внешний вызов как external» + учётом её в precision.

Все скомпилированные контракты — уязвимые reentrancy (метка SmartBugs), и все 4 помечены HIGH,
включая simple_dao (SimpleDAO) и reentrancy_simple (trailofbits) с *немодифицированным* исходником.
Нескомпилированное НЕ засчитано как покрытое.

**Что добавлено (frontend robustness, итерации 1-3):** `pragma`, `uint`=`uint256`, гибкая
visibility/`payable`/`constant`, **модификаторы** (инлайн), `+=`/`-=`, старый `.call.value(x)()`
и модерн-кортеж `(bool s,)=addr.call{value:}("")`, `throw`, единицы `1 ether`/`5 days`, `now`,
безымянный fallback `function(){}`, no-op выражение-инструкция, инициализаторы/атрибуты state-vars.

Добавлены также hex-литералы (`0x...`) и user-defined типы (контракт/интерфейс → address).

**Итерации 4-5 (эта сессия) — структурный batch, 8→29/31.** Закрыты доминирующие блокеры honeypot-
семейства: контракт-тип переменные + касты `Contract(x)` + `new Contract()` + кросс-контрактные вызовы
`obj.method()` (всё как opaque в sema); `var`-локали с выводом типа; тернарник `?:`; модуло `%`;
безтеловые функции-прототипы интерфейсов; коэрция ширины возврата/локали; **storage-ссылки `var acc =
map[key]`** (ключ к recall на honeypot'ах). Всё — без потери precision (курируемый корпус 0 FP).

**Оставшиеся 2 файла — многоблокерные:** `0x627f…` (нужен merge наследуемых state-vars из базы
`Ownable` + raw `.call(data,args)`), `spank_chain_payment` (вложенные `mapping(=>mapping)` + `bytes`).
Отдача за них низкая (2 файла, каждый требует нескольких структурных фич) — осознанно отложены.

**Вывод:** детектор корректен (адверсариально проверен) и даёт **recall 28/29 = 0.966 на всём
компилируемом независимом клоне** (24 реальных honeypot + классика), при **precision 1.0** на
курируемом корпусе с безопасными контрактами. Единственный FN — задокументированная граница метода.

Состав корпуса (см. `corpus/labels.csv`):
- **Уязвимые (HIGH):** классика; бизнес-флаг под видом guard (`require(active)`); запись в ветке `if`;
  несколько эффектов; `require(!paused)` без взведения флага; guard, снятый до вызова
  (`locked=true; locked=false; call`).
- **Безопасные (не HIGH):** CEI-корректный порядок; настоящий nonReentrant-guard (→ LOW); без внешнего
  вызова; вызов без записи после; только чтение после вызова; запись до вызова.

## Robustness baseline — почему реальные контракты SKIP-аются (2026-07-13, `hunt_batch.sh`)

Замер по плану `docs/ROBUSTNESS-PLAN.md` (шаг 0c). Бинарь выдаёт структурный код причины SKIP
(`SCSA_SKIP:*`, см. §2 плана); `hunt_batch.sh` бакетит. Живой RPC-feeder свежих 0.8 упёрся в
128КБ-кап free-эндпоинта (полноблочные методы усекаются) — поэтому directional-выборка курируемая
(крупные реальные 0.8: Seaport 1.1/1.5, Permit2, 1inch V5 + 0.4-ханипоты), НЕ случайная.

| адрес / контракт | версия | результат |
|---|---|---|
| Seaport 1.1 | 0.8.x | ✅ **lowered**, clean |
| Seaport 1.5 | 0.8.x | ✅ **lowered**, clean |
| Permit2 | 0.8.x | ✅ **lowered** (2×LOW) |
| 1inch AggregationRouter V5 | 0.8.x | ✅ **lowered** (1×MED, 22×LOW) |
| honeypot ×2 | 0.4.19 | SKIP `[C]` pre-0.8 |

**Ключевой вывод (скорректировал гипотезу плана):** крупные, assembly-heavy реальные **0.8**
контракты лоуэрятся УСПЕШНО — **0 отказов A1/A3/B1** на 4/4. Значит доминирующий SKIP в реальном
хвосте — **бакет C (pre-0.8, 0.4–0.7)**, а это НЕ баг лоуэринга, а честная граница охвата (мы
целимся в 0.8). Ранняя оценка «~90% SKIP» была из выборки, забитой 0.4-ханипотами.
**Следствие для приоритетов:** Фаза 1 (робастность лоуэринга 0.8) — НИЖЕ по отдаче, чем казалось;
0.8-путь уже рабочий. Рычаг к recall — не чинить фронтенд, а (а) фильтровать корпус на 0.8 и
(б) покрытие детекторов/инвариантов (уже строим). *Оговорка:* выборка мала и не случайна (известные
аудированные контракты); длинный хвост мелких/кривых 0.8 нужно домерить на RPC без 128КБ-капа.

## Честные оговорки (важно для интерпретации)

1. **Корпус самодельный.** Контракты написаны нами специально, чтобы покрыть целевые паттерны и
   ловушки детектора. Идеальные 1.0 подтверждают, что детектор корректен **на паттернах, которые
   он предназначен ловить** (включая антипаттерны-ловушки из адверсариального ревью), но это **НЕ
   независимый бенчмарк**. Сильное утверждение о precision/recall требует независимого корпуса.

2. **SmartBugs прогнан (независимый клон, 29/31).** Реальный корпус `smartbugs-curated/reentrancy`
   теперь компилируется на 29 из 31 файлов; recall на них **28/29 = 0.966** (1 задокументированный FN).
   Это независимые цифры на *немодифицированных* реальных контрактах. Осталось 2 многоблокерных файла
   (наследование state-vars, вложенные mapping, bytes) — вне метрики как «не скомпилировалось».
   Клон — датасет только уязвимых, поэтому по нему меряется recall; precision меряется на курируемом
   корпусе (11 безопасных, 0 FP).

3. **Известные границы детектора (future work):** одна находка на внешний вызов; атрибуция строки
   к эффекту, а не к вызову; guard распознаётся только как линейный паттерн из текущего codegen.
