# Бенчмарк precision / recall детектора reentrancy

Здесь лежит каркас для честной оценки детектора reentrancy проекта SCSA на внешнем
корпусе. Скрипт `run_benchmark.sh` прогоняет компилятор по каждому `.sol`, сравнивает
вердикт с ручной меткой и печатает precision / recall / F1.

## Важный дисклеймер про subset (читать первым)

Компилятор SCSA понимает **только подмножество Solidity**:

- типы: `uint256`, `bool`, `address` (никаких `mapping`, `struct`, `string`, `bytes`,
  массивов, `int*`, `uint8/…/uint128`);
- **один контракт на файл**, без наследования и интерфейсов;
- без событий (`event`/`emit`), модификаторов (`modifier`), библиотек, `using for`;
- без конструкторов со сложной логикой, без `assembly`.

Поэтому **значительная часть контрактов SmartBugs не скомпилируется** нашим фронтендом.
Такие файлы скрипт выносит в отдельную категорию **«не скомпилировалось»** с указанием
причины и **исключает их из метрики**. Мы принципиально **не** засчитываем
нескомпилированный файл ни как «покрытый», ни как «пропуск детектора» — иначе метрика
была бы нечестной.

Читайте итог так: precision/recall считаются **только по тем файлам, которые SCSA смог
скомпилировать**. Число «не скомпилировалось» показывает границу применимости subset —
его нужно приводить рядом с метриками, а не прятать.

## 1. Взять корпус SmartBugs

Используется `smartbugs-curated` — размеченный набор уязвимостей, папка `reentrancy`.

```bash
git clone https://github.com/smartbugs/smartbugs-curated.git
ls smartbugs-curated/dataset/reentrancy   # *.sol, все помечены как уязвимые
```

Все контракты в `dataset/reentrancy` считаются уязвимыми (reentrancy) — им ставится
метка `1`. Для честной оценки precision добавьте **безопасные** контракты (метка `0`) —
например, варианты тех же контрактов с исправленным порядком checks-effects-interactions,
или простые контракты без внешних вызовов.

## 2. Подготовить корпус под subset (опционально, но полезно)

Оригинальные файлы SmartBugs часто содержат `pragma`, несколько контрактов, `mapping`
и т.п. Можно скормить их «как есть» — не подходящие просто попадут в «не скомпилировалось».
Если хотите увеличить покрытие, вручную упростите ключевые контракты до subset (один
контракт, только `uint256/bool/address`) и положите в отдельную папку `corpus/`.

Пример минимального уязвимого контракта в рамках subset — `tests/fixtures/reentrancy.sol`
в этом репозитории.

## 3. Подготовить метки

Скопируйте пример и отредактируйте:

```bash
cp benchmarks/labels.example.csv benchmarks/labels.csv
```

Формат — `filename,expected_vulnerable`:

```
filename,expected_vulnerable
simple_dao.sol,1
safe_withdraw_cei.sol,0
```

- `filename` — базовое имя `.sol` (скрипт ищет его внутри папки корпуса, в т.ч. в
  подпапках, по `basename`);
- `expected_vulnerable` — `1` (уязвим) или `0` (безопасен);
- строки на `#` и пустые игнорируются; строка-заголовок пропускается.

Для всей папки `dataset/reentrancy` метки можно сгенерировать разом:

```bash
{ echo "filename,expected_vulnerable";
  for f in smartbugs-curated/dataset/reentrancy/*.sol; do
      echo "$(basename "$f"),1";
  done; } > benchmarks/labels.csv
# затем допишите свои безопасные контракты с меткой 0
```

## 4. Собрать компилятор

Бенчмарк **не собирает** проект. Соберите заранее:

```bash
export PATH=/usr/lib/llvm-18/bin:$PATH
cmake -S . -B build -G Ninja
ninja -C build
# бинарь: build/src/solidity-llvm
```

## 5. Запустить бенчмарк

```bash
./benchmarks/run_benchmark.sh <папка-с-.sol> <labels.csv> [путь-к-бинарю]

# пример:
./benchmarks/run_benchmark.sh smartbugs-curated/dataset/reentrancy benchmarks/labels.csv
```

Путь к бинарю можно задать третьим аргументом или переменной `SCSA_BIN`; по умолчанию
берётся `build/src/solidity-llvm`.

Скрипт вызывает `solidity-llvm --input <f> --audit --json`. Флаг `--json` пока не
реализован в CLI — скрипт это детектирует (по сообщению `Option 'json' does not exist`)
и автоматически откатывается на консольный режим. Классификация надёжно опирается на
**код возврата драйвера**:

| код возврата | значение                        | класс          |
|--------------|---------------------------------|----------------|
| `0`          | скомпилировалось, находок нет   | предсказ. «чист»|
| `2`          | скомпилировалось, есть находки  | предсказ. «уязвим»|
| `1`          | ошибка компиляции (subset)      | «не скомпилировалось» (вне метрики)|

Когда `--json` появится, скрипт подхватит его без изменений (он ещё и перепроверяет
вывод по тексту находок).

## 6. Как читать результат

Пример хвоста вывода:

```
--- сводка ---
  TP (уязвим, найден)        : 5
  FP (безопасен, найден)     : 1
  FN (уязвим, пропущен)      : 2
  TN (безопасен, чисто)      : 4
  в метрике всего            : 12
  не скомпилировалось (вне)  : 18
  нет файла (вне)            : 0

  precision : 0.8333
  recall    : 0.7143
  F1        : 0.7692

RESULT tp=5 fp=1 fn=2 tn=4 nocompile=18 missing=0 precision=0.8333 recall=0.7143 f1=0.7692
```

- **TP** — уязвимый файл, детектор нашёл reentrancy;
- **FP** — безопасный файл, детектор ошибочно нашёл (ложное срабатывание);
- **FN** — уязвимый файл, детектор промолчал (пропуск);
- **TN** — безопасный файл, детектор промолчал (верно);
- **precision** = TP / (TP + FP) — доля правды среди срабатываний;
- **recall** = TP / (TP + FN) — доля пойманных из всех реально уязвимых;
- **F1** — гармоническое среднее precision и recall.

Выше метрик печатается блок **«по файлам»** — построчный вердикт (`TP/FP/FN/TN/
NOCOMPILE/MISSING`) с причиной для нескомпилированных. Строка `RESULT …` в конце —
машиночитаемая, удобно грепать и собирать в таблицу.

**Всегда приводите рядом с precision/recall число `nocompile`** — оно честно показывает,
какая часть корпуса выходит за границы subset и в оценку не попала.
