# Неделя 1 на пальцах

Без понтов и без жаргона. Представь, что ты объясняешь подруге за кофе.

---

## Что такое компилятор

Компилятор — это переводчик. На вход ему даёшь текст программы на одном языке, на выход он выдаёт то же самое, но на другом — понятном машине (или следующему переводчику).

У нас:
- **Вход:** файл `.sol` — программа на Solidity (язык смарт-контрактов Ethereum).
- **Выход:** файл `.ll` — та же программа, записанная на **LLVM IR** (специальный промежуточный язык, с которым умеют работать умные инструменты анализа).

Мы пишем **только переводчик**. Анализаторы уязвимостей (это уже научная часть диплома) потом сами будут читать наш `.ll`.

---

## Что мы сделали на этой неделе (одной фразой)

Собрали **пустую коробку** будущего компилятора: структуру папок, сборку, командную строку, тесты. Сам переводчик внутри пока **ничего не переводит** — просто открывает файл и пишет заглушку. Это нормально: на первой неделе важно, чтобы всё это **собиралось и запускалось** на твоей машине.

---

## Из чего теперь состоит наш проект

Представь три коробки:

### Коробка 1. Движок (`solc_core`)
Здесь будет вся мозговая деятельность компилятора: читать текст, понимать грамматику, генерировать IR. Сейчас там только заглушка `Driver`, которая умеет открыть файл. Но коробка готова — в неё мы будем складывать всю будущую логику.

### Коробка 2. Обёртка (`solidity-llvm` — бинарник с командной строкой)
Это то, что ты реально запускаешь из терминала:
```
./solidity-llvm --input Counter.sol --emit-ir --output counter.ll
```
Обёртка ничего умного не делает — разбирает твои аргументы (`--input`, `--output`, ...) и вызывает движок из коробки 1.

### Коробка 3. Тесты (`unit_tests`)
Маленькие программки, которые проверяют: «а точно движок себя ведёт так, как мы ожидаем?». Запускаются командой `ctest`. Пока там 2 теста:
- движок ругается, если дать ему несуществующий файл,
- движок не падает, если дать существующий.

Когда добавим лексер/парсер/кодоген — тестов будет становиться больше.

## Зачем для этого столько всякой хрени

Ты правильно чувствуешь, что настройки много, а кода мало. Это нормально для первой недели любого серьёзного проекта. Объясню, на что ушла возня.

### CMake — «инструкция для сборки проекта»

У нас несколько `.cpp` файлов, куча зависимостей (LLVM, cxxopts, GoogleTest), нужно указать версию C++, флаги компилятора, пути к заголовкам… Руками каждый раз писать `g++ -std=c++20 -I... -L... -l... file1.cpp file2.cpp ...` — с ума сойдёшь.

**CMake — это IKEA-инструкция.** Ты один раз пишешь «вот из этих файлов собери такую библиотеку, слинкуй с LLVM, сделай из этого исполняемый файл» — а CMake потом сам разруливает, что в каком порядке компилировать. Мы говорим ему желание, он делает работу.

Файлы `CMakeLists.txt` у нас в трёх местах: корень проекта (общий), `src/` (как собирать код), `tests/` (как собирать тесты).

### LLVM — «чужой готовый компиляторный мозг»

LLVM — это огромная библиотека (~сотни мегабайт), которую написали другие. Она умеет:
- строить IR-код (Intermediate Representation — промежуточное представление),
- оптимизировать его,
- превращать в машинный код под разные процессоры,
- анализировать.

Мы **не пишем** всё это сами. Мы пишем только ту часть, которая принимает Solidity и строит LLVM IR через готовые классы типа `IRBuilder`, `Module`, `Function`. Всё остальное LLVM сделает за нас.

Чтобы наш проект мог пользоваться LLVM, в CMake написано «найди мне LLVM 18 на этом компьютере, подключи его библиотеки». На этой неделе мы не писали ни одной строчки, использующей LLVM, но **подключение уже готово** — со следующей недели оно понадобится.

### cxxopts — «парсер аргументов командной строки»

Когда ты запускаешь
```
./solidity-llvm --input Counter.sol --emit-ir
```
что-то должно разобрать эту строку и понять: «ага, `--input` это `Counter.sol`, `--emit-ir` это флаг-включатель». Это мог бы написать любой человек за час, но не надо — есть готовая библиотека cxxopts, где ты просто декларируешь:

```cpp
opts.add_options()
    ("i,input",    "Input .sol file", ...)
    ("emit-ir",    "Emit LLVM IR")
    ("h,help",     "Print help");
```

А она сама разбирает, валидирует, выдаёт `--help`-подсказку. Экономит время и нервы.

### GoogleTest — «автоматическая проверялка»

Ты написал код, он вроде работает. Но через неделю ты поменяешь что-то в одном месте, и случайно сломаешь другое. Как это поймать?

Тест — это маленький кусок кода, который пишет «вот такой вход, вот такой ожидаемый выход, проверь». Запускаешь все тесты — если все зелёные, значит ты ничего не сломал.

GoogleTest — это просто популярный фреймворк для таких проверок. Мы пишем:
```cpp
TEST(Smoke, DriverRejectsMissingFile) {
    // дали несуществующий файл — ожидаем ошибку
    ...
}
```
и он автоматически запускает всё и показывает, что зелёное, что красное.

### Git — журнал изменений

Это ты уже знаешь. Каждое осмысленное изменение — отдельный **коммит**. У нас их за неделю 5:
```
docs: readme with build & run instructions
test: smoke tests for Driver via GoogleTest
feat: stub CLI and Driver linked against LLVM
build: CMake skeleton with LLVM 18.1 and FetchContent deps
chore: init repo with gitignore
```
Читаешь сверху вниз, и становится видно **как проект рос**. Это полезно и для тебя (вспомнить «что я делала в тот вторник?»), и для защиты курсовой (научник увидит, что ты работала системно).

## Что конкретно работает прямо сейчас

Ты можешь в терминале Ubuntu сделать так:

```bash
cd ~/diplom/solidity-llvm
cd build
./src/solidity-llvm --help
```

И увидеть:
```
Solidity subset -> LLVM IR compiler (MVP)
Usage:
  solidity-llvm [OPTION...]

  -i, --input arg   Input .sol file
  -o, --output arg  Output file (default stdout)
      --emit-ir     Emit LLVM IR
  -h, --help        Print help
```

Можешь даже скормить ему файл:
```bash
echo "contract X {}" > /tmp/x.sol
./src/solidity-llvm --input /tmp/x.sol --emit-ir
```
И он выдаст:
```
; solidity-llvm: stub output, source length=14
```

Это **заглушка**. Он просто прочитал файл, посчитал сколько там символов, и сообщил. Ничего компиляторского он пока не делает. Но инфраструктура для этого уже готова — со следующей недели внутрь этой заглушки мы начнём класть настоящую логику.

А ещё можешь прогнать тесты:
```bash
ctest --output-on-failure
```
И увидишь:
```
1/2 Test #1: Smoke.DriverRejectsMissingFile ....   Passed
2/2 Test #2: Smoke.DriverAcceptsExistingFile ...   Passed
```

Оба зелёные. Значит базовый каркас работает.

## Почему много букв ради заглушки — это нормально

В любой большой программе самая **скучная** часть — скелет. Когда ты первый раз его собираешь, есть ощущение «я потратила два часа, а программа почти ничего не делает». Это иллюзия: ты потратила два часа на то, чтобы **следующие 50 часов работы шли быстро и без спотыкания**.

Аналогия: готовить борщ. Первые 20 минут ты моешь, чистишь, режешь овощи. Ничего **вкусного** за эти 20 минут не появилось — но без них борща вообще не будет.

У нас сейчас овощи помыты и порезаны. Со следующей недели начинается готовка.

## Что будет на неделе 2

Напишем **лексер** — первую настоящую часть компилятора.

Лексер — это программа, которая берёт текст и разбивает его на **слова**. Например, для строчки:
```solidity
uint256 x = 42;
```
лексер выдаст список:
```
[ключевое_слово uint256] [идентификатор x] [знак_равно =] [число 42] [точка_с_запятой ;]
```

Это ещё не понимание программы — это просто разделение на «единицы смысла». Следующая часть (парсер, неделя 3-4) будет складывать из этих кусочков дерево.

## Если запутаешься

Ты не осёл. Этот стек технологий (CMake + LLVM + C++ + тесты) — это примерно то, что обычный junior C++ разработчик осваивает за полгода работы в команде. Ты же пытаешься за неделю настроить это в одиночку, плюс ещё делать содержательную работу. Это **реально много**.

Если какой-то кусок непонятен — спрашивай про конкретную штуку: «что такое `PUBLIC` в CMake?», «зачем `static` library?», «что такое namespace?». Я объясню на твоём текущем уровне, а не на уровне документации LLVM.
