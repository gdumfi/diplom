# Неделя 2 на пальцах — лексер

---

## Что такое лексер

Представь, что тебе дали книгу на чужом языке и попросили её перевести. Первое, что ты делаешь, — **разбиваешь её на слова**. Ты пока не понимаешь смысл, просто отделяешь слово от слова.

Лексер делает ровно это с кодом. На входе — сплошной текст:
```solidity
uint256 public value;
```
На выходе — список «смысловых кусочков», которые называются **токенами**:
```
[KwUint256: "uint256"] [KwPublic: "public"] [Identifier: "value"] [Semicolon: ";"]
```

Лексер не понимает, что `uint256` — это тип, а `value` — имя переменной. Он просто говорит: «вот это слово целое число типа `KwUint256`, а это — идентификатор». Смысл будет собирать **парсер** (это неделя 3).

---

## Зачем вообще нужен этот этап

Почему не парсить текст напрямую? Потому что было бы **очень** сложно. Парсеру одновременно пришлось бы думать о пробелах, комментариях, многосимвольных операторах (`==` vs `=`), ключевых словах vs идентификаторах — и ещё о грамматике языка.

Разделение труда: лексер убирает весь «шум» (пробелы, комментарии) и классифицирует каждое слово. Парсеру остаётся работать с чистым потоком токенов.

---

## Что мы написали на этой неделе

### Три новых класса

**1. `DiagnosticEngine` — сборник ошибок**

Когда компилятор видит что-то плохое (например, символ `@` в Solidity), он **не бросает исключение** и не падает. Он записывает ошибку в `DiagnosticEngine` и продолжает работать. Это важно: если у тебя в файле 10 ошибок, ты хочешь увидеть все 10 сразу, а не по одной (как если бы компилятор падал после первой).

Внутри — просто вектор структур `{line, col, message}`. Ничего космического.

**2. `Token` + `TokenKind` — словарь категорий**

`TokenKind` — это `enum class` из 35 значений. По сути, список «все возможные типы слов в нашем языке»:
- `Identifier` — любое имя (value, owner, increment, foo, bar_42...)
- `Number` — любое число
- `KwContract`, `KwFunction`, `KwIf`, ... — ключевые слова
- `Plus`, `Minus`, `EqEq`, ... — операторы
- `LParen`, `LBrace`, ... — скобки и знаки препинания
- `EndOfFile` — «всё, текст закончился»
- `Invalid` — «я не понял, что это»

`Token` хранит: тип (`TokenKind`), кусочек исходного текста (само слово, как `std::string_view` — это **указатель** в исходник без копирования), и позицию `{line, col}` для ошибок.

**3. `Lexer` — сама машина разбиения**

Главный метод `next()` возвращает один токен за раз. Внутри:
1. Пропустить пробелы и комментарии.
2. Если дошли до конца — вернуть `EndOfFile`.
3. Посмотреть на первый символ:
   - буква или `_` → читаем слово, потом смотрим в таблицу ключевых слов. Если совпало — ключевое слово, иначе — `Identifier`.
   - цифра → читаем число.
   - `=` → может быть `=` или `==`. Смотрим следующий символ.
   - Аналогично `<`, `>`, `!`, `&`, `|`.
   - Одиночные знаки препинания — напрямую.
   - Всё остальное — записываем ошибку «unexpected char» и возвращаем `Invalid`.

## Хитрости, которые стоят объяснения

### `std::string_view` вместо `std::string`

Представь, что у тебя файл `counter.sol` длиной 400 байт, и ты его уже загрузил в одну большую строку. Каждое слово — кусочек этой строки. Если бы для каждого токена мы делали `std::string` (копию), получилось бы 80+ маленьких копий — лишняя память и замедление.

`std::string_view` — это **указатель + длина**, никакого копирования. Он просто говорит: «вот в исходнике с 15 по 22 байт лежит лексема `uint256`». Весь наш Lexer — **zero-copy**.

Цена: кто-то должен держать исходник живым, пока мы им пользуемся. Это ответственность Driver'а (он будет хранить string с файлом).

### `advance()` и позиция

```cpp
char Lexer::advance() {
    char c = src_[pos_++];
    if (c == '\n') { loc_.line++; loc_.col = 1; }
    else           { loc_.col++; }
    return c;
}
```
Продвигаемся на 1 символ вперёд и обновляем номер строки/колонки. На `\n` прыгаем на следующую строку. Это даёт нам возможность сказать пользователю «ошибка на строке 7, колонка 12», а не «ошибка на 142-м байте».

### Захват позиции ДО `advance`

Важный момент: когда мы начинаем читать токен, мы сначала **сохраняем** текущую `{line, col}`, и только потом двигаемся. Иначе позиция токена была бы после его конца, а не в начале. Пример:
```
   12345
   abc xy
```
Токен `abc` должен иметь `loc={1, 1}`, а не `{1, 4}`.

### Почему `match('=')` — элегантно

Для различения `=` и `==`:
```cpp
case '=':
    if (match('=')) return makeToken(TokenKind::EqEq, ...);
    return makeToken(TokenKind::Eq, ...);
```
`match('=')` возвращает `true` **и сдвигается**, если следующий символ — это `=`. Одним вызовом проверяем и потребляем. Без этого пришлось бы писать `peek() == '='` а потом отдельно `advance()`.

### Ключевые слова и идентификаторы — одна общая процедура

Для лексера `contract` и `foo` выглядят одинаково: буква-за-буквой-цифра. Он читает «слово» до первого не-буквы-не-цифры, потом **проверяет в таблице**: есть ли в списке ключевых слов? Если да — возвращает соответствующий `TokenKind`. Если нет — `Identifier`.

```cpp
static constexpr std::pair<std::string_view, TokenKind> kws[] = {
    {"contract", TokenKind::KwContract}, ...
};
```
13 записей — обычный линейный поиск. Хеш-таблица тут была бы overkill.

## Что теперь умеет компилятор

Пока — всё так же принимает `.sol`-файл и печатает заглушку. **Но мы научились читать его правильно:** все поддерживаемые токены корректно распознаются.

Чтобы это увидеть — придётся подождать неделю 8. Тогда мы добавим флаг `--tokens`, который будет печатать поток токенов для отладки. Сейчас у лексера нет пользовательского фасада — только внутренние тесты.

Что можно сделать прямо сейчас:
```bash
cd ~/diplom/solidity-llvm/build
ctest --output-on-failure
```
И увидеть:
```
11/11 tests passed
```
Из них 8 — проверки лексера на разных входах, включая реальный `counter.sol`.

## Что работает под капотом (на примере)

Вход:
```solidity
uint256 x = 42;
```

Лексер выдаёт (по вызовам `next()`):
```
Token{kind=KwUint256,  lexeme="uint256", loc={1,1}}
Token{kind=Identifier, lexeme="x",       loc={1,9}}
Token{kind=Eq,         lexeme="=",       loc={1,11}}
Token{kind=Number,     lexeme="42",      loc={1,13}}
Token{kind=Semicolon,  lexeme=";",       loc={1,15}}
Token{kind=EndOfFile,  lexeme="",        loc={1,16}}
```

Пять смысловых кусочков + EOF. Парсер на следующей неделе начнёт из этого строить дерево.

## Про Russian + lowercase-start комментарии

Ты попросила — сделали. В файлах `Token.h`, `Lexer.h`, `Lexer.cpp` и `Diagnostic.h` все комментарии русские и начинаются с маленькой буквы:
```cpp
// позиция в исходнике, 1-based для line и col
// таблица ключевых слов — compile-time порядок не важен, поиск линейный
```
Код от этого не зависит, но читать проще. Правило теперь в памяти, сабагенты его соблюдают.

## Что дальше — неделя 3

Парсер. Берёт поток токенов от лексера и строит **дерево** (AST — Abstract Syntax Tree). Например, для `uint256 x = 42;` получим:
```
VarDecl
├── type: Uint256
├── name: "x"
└── init: NumberLit("42")
```

На неделе 3 парсим только «скелет» контракта: `contract Name { state-vars; функции-заголовки; }`. Внутренности функций (statements, expressions) — неделя 4.
